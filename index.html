IBM Bob on Netcool code

Five prompts that take a Netcool Impact policy and a set of Netcool probe rules from a defect register to fixed, cleaned, standardized and reviewed code, with IBM Bob in its built-in Agent mode.

Pilot use case for a telecom operator · 3 October 2026

Second use case: adding a device to a Netcool dashboard, and debugging it · The skill behind both: the code-review skill for IBM Bob

The use case

Use case 5 of the pilot is code analysis, standardization and optimization for Netcool: Impact policies and probe rules that grew over years, with defects nobody has listed, commented-out code left in place, hard-coded paths and inconsistent names. The client sent two pieces of production code, each with its own document saying what the code should become:

An Impact policy

About 3,300 lines that build an incident ticket from an alarm and send it on. Its guide is the client's refactoring requirement document: defects to fix, logging and dead code to tidy, camelCase naming, and a three-tier modular structure.

Probe rules

About 1,900 lines of rules for one element manager, with ten lookup files. Its guide is the client's code standards document: no hard-coded values, paths through an environment variable, one log format, no commented-out code, and a standard directory tree.

Nothing here runs on an Impact server or on a probe. Everything the prompts claim is shown from the code alone, and every report says what still needs a test where the code runs.

How it works

Bob is opened on one workspace folder that holds both inputs, each in its own folder with its document. Two small things in that folder steer it:

One skill: code-review

Instructions for five tasks (review code, fix, change existing code, review a change, diagnose) and a set of Python scripts that do the mechanical work. The skill is generic: it names no client, product or language.

A short rule

Tells Bob to use the skill before any review or change, to run its commands from the workspace root, and to check where the work stands before every reply.

The scripts do the work, Bob does the judging

Each task is one command, run twice or three times. The first run scans the code and writes a notes file with everything Bob has to decide. Bob reads the code and writes its judgements in that notes file: which scan hits are real defects, which corrections to make, what the client must decide. The next run applies the notes, writes the report and the changed copy, and compares the new version with the old one. The scripts write every report and every changed file; Bob never types code or reports by hand.

Gates

Every command ends with a line that starts Gate:. A task is finished only when it prints Gate: passed. A gate refuses, for example:

  • a review where a scan hit was left undecided, or a quoted line is not on the line it cites;
  • a fix that leaves a High finding with no correction and no specific question for the client;
  • a change that adds a call, an operator or a non-ASCII character the original did not have, unless the reason is written down;
  • a change that leaves a file with half a block, or a requirement of the client's document unaccounted for;
  • a review of a change where any difference between the two versions has not been judged.

A gate that passed means the work is complete and accounted for. It does not mean the code is right; that is what the reports and the last prompt are for.

One chat for everything

All five prompts go in one chat. Long chats get summarized by Bob on the way; a status command lets Bob see, from the files, which tasks are finished and which request it is answering, so it picks up where it was.

The five prompts

Each prompt does its step for the policy and then for the rules. Each step works on the output of the one before; the original files are never changed. The texts below are the prompts as sent, with the client's name replaced by "the client".

1Defect registerreview, no change

Bob scans and reads each file, decides each scan hit, adds what reading finds, and writes a register: every defect with its line, the quoted code, its effect on the ticket or the event, the fix, and how sure it is.

Review the policy in impact-policy/inputs and the rules file in probe-rules/inputs for defects, one after the other, each with the document from the client next to it as the guide.
Write impact-policy/reports/defect-register.md and probe-rules/reports/defect-register.md, with the effect of each defect on the ticket for the policy and on the event for the rules.
Do not change the policy or the rules file.
2Fixcorrected copy and change log

The script makes every correction that has only one possible form (a single = in a condition, a name missing its prefix, a misspelt field). Bob corrects what the code shows to be right and leaves every real choice to the client as a specific question. A correction that would hide a defect is held back as a proposal.

Fix the defects of the policy in a copy under impact-policy/refactored/step-1-fixed and the defects of the rules file in a copy under probe-rules/refactored/step-1-fixed, one after the other.
Log the changes in impact-policy/reports/change-log.md and probe-rules/reports/change-log.md.
Leave what is a decision for the client.
3Clean upcommented-out code removed

The script lists the commented-out code (lines switched off, disabled statements, whole blocks); Bob decides what goes, and the script removes it in a copy. The events and tickets stay the same.

Clean up a copy of each step-1-fixed, one after the other, keeping the ticket content and the events the same.
Policy: in a copy of impact-policy/refactored/step-1-fixed under impact-policy/refactored/step-2-cleaned, remove the commented-out code as section 3 of the requirement document asks. Report in impact-policy/reports/clean-up.md.
Rules: in a copy of probe-rules/refactored/step-1-fixed under probe-rules/refactored/step-2-cleaned, remove the commented-out code as standard 4 of the code standards document asks. Report in probe-rules/reports/clean-up.md.
4Standardizenames and paths

Policy: every local variable renamed to camelCase from the script's proposals, except names that another component may read or that may come from outside. Rules: the absolute path prefix replaced by an environment variable with one rule, so that nothing else in those lines can change.

Standardize a copy of each step-2-cleaned, one after the other, keeping the ticket content and the events the same.
Policy: in a copy of impact-policy/refactored/step-2-cleaned under impact-policy/refactored/step-3-standardized, rename the variables to camelCase as section 3 of the requirement document asks. Report in impact-policy/reports/standards.md.
Rules: in a copy of probe-rules/refactored/step-2-cleaned under probe-rules/refactored/step-3-standardized, replace the absolute path prefix /opt/IBM/tivoli/netcool/omnibus/etc/probes/rules with $NC_RULES_HOME in every include and table line, as standard 2 of the code standards document asks. Change only that prefix: every folder and file name after it stays as it is. Report in probe-rules/reports/standards.md.
5Code reviewthe final copy against the original

The script compares the final copy with the original and writes the review: both versions in numbers, the defect counts before and after, what the change consists of line by line, and every difference for Bob to judge as no change of behaviour, intended or unintended. Bob adds what reading finds, checks the claims of the earlier reports, and says what only the client can settle.

Review impact-policy/refactored/step-3-standardized against the original policy in impact-policy/inputs, and probe-rules/refactored/step-3-standardized against the original rules file in probe-rules/inputs, one after the other.
Write impact-policy/reports/code-review.md and probe-rules/reports/code-review.md.
Do not fix anything.
The client's documents also ask for more than these five prompts do: a split into a modular structure, merged database queries, rewritten log statements, and lookup files for hard-coded values. Those were tried and are kept aside: where Bob had to write new code itself, the result varied from run to run and was sometimes wrong while its gate passed. The five prompts above keep to what the scripts make reliable.

What the rehearsals showed

The prompts were rehearsed in Bob from a clean workspace, with nothing typed in the chat but the five prompts, and every step was checked by hand against the original before the next prompt was sent. A step counts as right only when its gates passed and the changed copy held when read line by line.

What the rehearsals teach

  • Where a script makes the change, the result is the same and right every time. Corrections that have one possible form, removal of the commented-out code the script listed, renames from the script's proposals, one rule for a path prefix.
  • Where Bob writes new code itself, the result varies from run to run and was sometimes wrong while its gate passed: rewritten log lines, new lookup files, a split into modules. Those are kept out of the five prompts until they hold.
  • A gate is necessary, not sufficient. It proves the work is complete and accounted for, not that it is right. Read each step's report and diff before sending the next prompt.
  • Read what Bob writes in its own words. The scripts check every line of code and every count they produce; they cannot check a reason, a question or a number Bob types into a review. Those were wrong in places, so the reviews are read before they are presented.
  • Leave the client's decisions to the client. When the review leaves a finding to the owner, the fix lists its correction as a proposal with a specific question instead of applying it.
  • Long chats need a way back. Bob summarizes a long chat on the way; the status command lets it see from the files which tasks are done and which request it is answering.
  • Plan for the turn limit. Five prompts on two inputs take more than Bob's default 100 turns per task; raise the limit before the session or be ready to click "Continue Task".

Running it

  1. Open the workspace folder itself in IBM Bob, not its parent.
  2. In Bob's settings, raise the limit on the number of turns of a task above its default of 100; the five prompts in one chat need more.
  3. Start a new chat in the built-in Agent mode and send the five prompts in order, one after the other, and nothing else.
  4. After each prompt, Bob's commands should have printed Gate: passed twice, once for each input. Read the reports before sending the next prompt.
