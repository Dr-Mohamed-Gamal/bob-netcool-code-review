The code-review skill for IBM Bob

One generic Bob skill that makes Bob's work on existing code repeatable and verifiable: it reviews code, fixes it, changes it, reviews a change and diagnoses a failure, in any language, and proves each step with a gate.

Built for a telecom operator's pilot · 3 October 2026

What it is

A Bob skill is a folder in .bob/skills/: a SKILL.md that tells Bob when to use it and how, and the tools it brings. This one holds a set of Python scripts that do the mechanical work, so that Bob spends its effort on judgement:

Bob decides

Which scan hits are real defects, what the right correction is, what to copy and under which names, which difference is intended, what only the owner can settle.

The scripts do

Scan the code, write every report and every changed file from Bob's notes, compare the new version with the old one line by line, and refuse to finish while anything is unexplained.

Every command ends with a line that starts Gate:. A task is finished only when it prints Gate: passed.

Generic by design

The skill names no client, product, platform or language. Nothing in its instructions or scripts refers to the code it was tried on. That is checked: a search of the skill for the client's names, the product's names and the names in its code finds nothing.

  • Any language. The scripts read code as text. Comment styles are recognised from the files (// and /* */, #, --); in a web page, only its scripts and event attributes are read as code.
  • The client's rules come from the client's documents. A requirement or standards document placed next to the code is read by the scripts: lists of names and types are used by the scan, and each change must say what it does about each sentence of the document.
  • One skill, many kinds of code. In the pilot the same skill, unchanged between them, handled an event-processing policy, a set of event-probe rules and an operations dashboard page.
  • Tested on its own code. 668 automated tests run on small synthetic samples, none taken from a client.

The five tasks

TaskCommandWhat Bob gets
B. Review coderun.py review <code> --out <report>A defect register: every scan hit decided as a finding or not, findings from reading that quote their line, the effect of each defect, the fix, and the questions for the owner.
D. Fixrun.py fix <code> --out <folder> --log <log> --register <review>A corrected copy and a change log. Corrections with one possible form are made by the script; Bob's corrections come with a worked example; what is the owner's to decide is proposed, not applied.
E. Change existing coderun.py edit <code> --out <folder> --report <report>Clean-ups, renames, rules over many lines, splits into files, and copies: a new item made exactly like an existing one, wherever the model appears. The report accounts for every difference.
A. Review a changerun.py change <before> <after> --out <review>A review written by the script: both versions in numbers, the change line by line, every difference for Bob to judge as intended, unintended or without effect, and the claims of the earlier reports checked.
C. Diagnoserun.py diagnose <code> --out <report>From a symptom to the line: every line that names what the symptom involves, the scan hits on them, and each possible cause with its quoted line, shown, ruled out, or open with the test that decides it. Nothing is changed.

Two more commands help: run.py status lists every task started in the workspace and whether its gate passed, so Bob always knows which request it is answering, even after a long chat is summarized; run.py look <code> counts what the code holds.

How a task runs

  1. First run. The script scans the code and writes a notes file next to the report: the facts to start from and the form to fill.
  2. Bob writes its judgement in the notes: decisions, corrections, a plan, causes. It never writes the report or the changed code itself.
  3. Next run. The script applies the notes, writes the report and the copy, compares the copy with the original, and lists what is still open.
  4. Repeat until the command prints Gate: passed. Then Bob gives the user the verdict, the counts and the gate line as printed.

What the gates refuse

  • a scan hit left undecided, or a quote that is not on the line it cites;
  • a High finding with no correction and no specific question for the owner;
  • a change that adds a call, an operator, a string or a non-ASCII character without saying why;
  • a file left with half a block, or a requirement of the client's document left unaccounted for;
  • a removed comment that explains live code that stays;
  • a copy that still holds a name of its model in any letter case, reuses a name the code already has, is not a whole block, or keeps a style value that does not fit the new name;
  • a review with any difference left unjudged, and a diagnosis with no cause shown or open.

A gate that passed means the work is complete and accounted for. It does not mean the code is right on the live system: the reports say what still needs a test there.

Using it

  1. Copy the skill folder into the workspace as .bob/skills/code-review/.
  2. Add a short rule in .bob/rules/ that tells Bob to use the skill before any review or change, to run its commands from the workspace root, and to run status before every reply.
  3. Put each body of code in its own folder, with the documents that came with it.
  4. Write each prompt in the same three parts: a first line that starts with the verb of the task and says what and where, then Write <report>., then a Do not ... line. The verb picks the task: Review (code, or a change against its baseline), Fix, Clean up / Standardize / Rename / Split / Add, Diagnose. For example: "Add the device NEW, modelled on the device OLD, to a copy of inputs/page.html under refactored/step-1. Write reports/add-device.md. Do not change inputs."
The skill sits with Bob's other building blocks: the requirement says what, Bob's rules hold the conventions that always apply, and the skill holds how and the checks that prove it. It can be shared across teams through the Bob Marketplace.
