IBM Bob on Netcool code · second use case · the skill

Adding a device to a Netcool dashboard

Prompts that let IBM Bob add a new device to an existing Netcool Impact dashboard with exactly the same tiles, filters and selection as the devices already on it, review that change, fix what the review finds and review the fix, and, apart from that sequence, debug a fault reported on the dashboard.

Pilot use case for a telecom operator · 3 October 2026

The use case

The operator's dashboard is a Netcool Impact Operator View page: HTML with inline JavaScript, fed every minute by an Impact policy. It lists about twenty network devices. Each device has a checkbox that adds it to the overview counts, and three tiles, Critical, Major and Minor, that open the Event Viewer filtered on that device's alarms. Every device is also named in the page's "select all" and "unselect all" functions.

The request: Bob must be able to edit the dashboard to add a new device when one comes into service, so that the new device has the same dashboard attributes as the others. The demonstration uses mock data, since the policy and the scripts that fill the counts on the live system were not part of the package.

Why not let Bob edit the page freely

Copying a device by hand is about ten lines, and Bob gets it right most of the time. The first use case showed where it goes wrong: when Bob types new lines itself, the result varies from run to run, and nothing flags a mistake. The typical mistakes here would be invisible on the page:

  • one tile keeps the old device's filter name, so it opens another device's alarms;
  • the device is missing from one of the select lists, so "select all" leaves it out;
  • an element id is mistyped, so its count never shows.

So the change is made by a script, and Bob only decides what to copy and what to call it.

How it works

The same generic code-review skill as in the first use case gained one operation in its change task: a copy. Bob names the model device, the block of lines that is its row, and the other spellings of its name. A made-up example:

### copy sw1 as sw2
lines: 40-47
replace:
  F_SW1_ -> F_SW2_
  SW1 -> SW2
why: the owner asks for the device SW2, with the same tiles, filters and selection as SW1.

The script then:

  • copies the model's block right after itself, with only those replacements;
  • finds every other line of the page that names the model (the select lists) and copies each one right after itself, the same way, so the new device is wherever the model is;
  • refuses the copy while it still holds any name of the model, so no tile can keep an old filter;
  • refuses a new name the page already uses, so ids and filter names stay unique;
  • refuses a block that is not whole, one that closes a tag it never opened or the reverse, so the layout cannot break;
  • accounts in its report for every string and call it repeated, so the comparison of the two versions has nothing unexplained.

The result is the model row, character for character, under new names, and the gate proves it.

Web pages as code

The skill's scanner reads code as text in any language. In a web page it now reads only the scripts and the event attributes (onclick, onchange), keeping the line numbers of the page. On the operator's dashboard that took the scan from 110 places, almost all markup noise, to 2.

Debugging, as a task with a gate

The skill's diagnosis task used to be instructions only. It is now a command with a gate, like the others:

  • Bob writes the symptom, in the reporter's words, and the names it involves;
  • the script lists every line of the code that names them, with the scan hits on those lines;
  • Bob writes each possible cause with its line, a quote that must be on that line, how the line produces the symptom, and whether the evidence shows it, rules it out, or which test would decide it;
  • the gate passes only when a cause is shown, or every remaining cause names the test that decides it. Nothing in the code is changed.

The prompts

A closed loop of four prompts: add, review, fix, review the fix. Prompts 3 and 4 are repeated until the review is clean; when the review finds nothing, the fix passes at once without changing anything. Debugging is a separate prompt, used whenever a fault is reported. The names in angle brackets are filled in for the device being added and the fault being reported.

1Add the devicea copy, under names of its own
Add the device <NEW DEVICE>, with DeviceType '<NEW DEVICE>', modelled on the <MODEL> device, to a copy of inputs/<page>.html under refactored/step-1-device-added: the same tiles, filters and selection, under names of its own.
Write reports/add-device.md.
Do not change inputs.
2Review the changethe copy against the original
Review refactored/step-1-device-added against inputs/<page>.html.
Write reports/code-review.md.
Do not fix anything.

Every prompt has the same three parts: a first line that starts with the verb of the task (Add, Review, Diagnose, Fix) and says what and where; Write and the report; Do not and the limit. The verb tells Bob which task of the skill to run, so it starts at once.

3Fixthe findings of the review
Fix the findings of reports/code-review.md in a copy of refactored/step-1-device-added under refactored/step-2-fixed.
Write reports/change-log.md.
Do not decide what is the client's to decide.
4Review the fixthe fixed copy against the original
Review refactored/step-2-fixed against inputs/<page>.html.
Write reports/code-review-2.md.
Do not fix anything.
5Debugseparate: from a reported symptom to the line
Diagnose inputs/<page>.html: the <DEVICE> tiles open the alarms of <OTHER DEVICE> instead of those of <DEVICE>.
Write reports/diagnosis.md.
Do not fix anything.
Short prompts keep the run short and cheap in Bob coins. The model device should be one whose names are its own; the review step shows anything the copy shares with other devices.

Running it

  1. Open the dashboard's workspace folder in IBM Bob. It holds the page under inputs/ and the skill under .bob/.
  2. Start a new chat in the built-in Agent mode and send the prompts in order, with the names filled in.
  3. After each prompt, Bob's command should end with Gate: passed. Read the report it names before sending the next one.
This page describes the method and the prompts only. The operator's dashboard, its device names and the reports made from it are not published here.
